# AI Sourcing Agent - SKELAR (MVP)

Автономний Streamlit-додаток для пошуку кандидатів: Apify (LinkedIn) + Claude
(4 AI-агенти: Strategist, ATS Checker, Strict Evaluator, Critic).

## Що вже працює

- Agentic loop: шукає, поки не набере потрібну кількість A-tier кандидатів,
  або поки не вичерпає safety limit (кількість ітерацій задається в сайдбарі).
- Human-in-the-loop чекпоінт: цикл виконує РІВНО одну ітерацію і зупиняється,
  показує проміжний результат і дає текстове поле "Корективи для наступної
  ітерації" (напр. "шукай ще в Львові", "тайтл X не підходить"). Рекрутер тисне
  або "Продовжити", або "Завершити зараз і показати фінальний список".
  Це навмисно - без цього цикл крутився б наосліп до кінця без можливості
  втрутитись, а Streamlit технічно не вміє "заморозити" один суцільний цикл
  і чекати відповіді в реальному часі - тому чекпоінт після кожної ітерації
  це правильна архітектура саме для Streamlit, а не спрощення.
- Strategist сам перебудовує пошуковий запит, якщо попередня ітерація дала
  мало результатів, і враховує корективу рекрутера як пріоритет №1. Усі
  альтернативні тайтли об'єднуються ОДНИМ boolean-рядком через OR у
  searchQuery (а не паралельно ще й у currentJobTitles) - бо Apify застосовує
  ці два поля як AND, і в комбінації з локаціями це давало 0 результатів
  навіть коли кандидати реально були (знайдено емпірично, звірено з робочим
  скілом /sourcer-ai).
- Курсор сторінок видачі: кожен унікальний запит (searchQuery+locations)
  пам'ятає, на якій сторінці зупинився, і наступна ітерація з тим самим
  запитом тягне наступну сторінку, а не повторно першу.
- PM-агент усередині ітерації: якщо Apify повертає помилку або підозріло 0
  профілів, Claude не чекає сліпо наступної повної ітерації - одразу
  аналізує ймовірну причину (невизнана локація, конфлікт полів, задовгий
  boolean-запит тощо) і сам лагодить і повторює запит, до 3 спроб
  (`MAX_APIFY_ATTEMPTS_PER_ITERATION` в коді). Кожна спроба і діагноз видно
  в логу "📜".
- Strict Evaluator: hard-stop по локації/громадянству (ніколи не Росія,
  перевірка по структурованому полю `location.parsed` з реальних даних
  актора), hard-stop по стоп-листу компаній - але ТІЛЬКИ якщо це поточний
  роботодавець (`currentPosition`). Колишні працівники стоп-компаній
  (`experience` з завершеною датою) - це не hard stop, а ціла цільова
  аудиторія, і в таблиці результатів це видно приміткою "Ex-[компанія]".
  Розрахунок релевантного досвіду (YOE) окремо від загального.
- Critic: перевіряє висновок Evaluator-а на галюцинації, пропускає далі
  тільки кандидатів з "perfect score".
- Результати: таблиця з чекбоксами + експорт обраних у CSV.
- Google X-ray (паралельний канал у тій самій ітерації, вмикається чекбоксом
  у сайдбарі): окрім прямого LinkedIn-пошуку, шукає ще й через звичайний
  Google (`site:linkedin.com/in ...`) тим самим Apify-токеном - без окремого
  Google API key. Знайдені URL дотягуються до повного профілю окремим
  актором і йдуть у той самий Evaluator/Critic. У таблиці результатів є
  колонка "Джерело", щоб було видно, звідки прийшов кандидат.
- Самонавчання - справжня пам'ять між сесіями, без ручного копіювання
  ("🧠 Пам'ять про вирішені проблеми" в сайдбарі): коли PM-агент сам
  діагностує й лагодить проблему з Apify-запитом (нерозпізнана локація,
  конфлікт полів тощо), він перевіряє, чи це вже відомий випадок, і якщо ні -
  формулює короткий урок ("Проблема: ... → Рішення: ...") і одразу зберігає
  його в персональний **Apify Key-Value Store** (той самий акаунт і токен,
  що вже й так введений для пошуку - жодного додаткового ключа чи сервісу).
  Кожна наступна сесія - навіть через тиждень, навіть в іншому браузері -
  сама підвантажує накопичені уроки і враховує їх заздалегідь, і Strategist,
  і PM-агент більше не витрачають спробу на те, що вже колись з'ясували.
  Це і є "агент сам навчається": людині нічого копіювати чи вставляти не
  треба. На випадок, якщо PM-агент колись зробить хибний висновок і запише
  його як "урок" - у сайдбарі є кнопка "🗑️ Очистити пам'ять", щоб не
  застрягнути з неправильним правилом назавжди.
- Самонавчання на фідбеку рекрутера ("🎯 Фідбек рекрутера" в сайдбарі): на
  екрані результатів у кожного кандидата є колонка "Причина відхилення"
  (готові категорії - "Замало B2B досвіду", "Часто змінює роботу", "Слабкий
  стек" - або "Інше" з вільним текстом). Кнопка "💾 Зберегти фідбек для
  навчання AI" пише ці приклади в той самий персональний Apify Key-Value
  Store (окремий ключ `recruiter_feedback`, спільний на всі вакансії, бо
  смаки рекрутерки зазвичай не прив'язані до однієї ролі). Далі ⚖️ Суддя
  (Evaluator) бачить ці приклади в кожній наступній оцінці і намагається не
  ставити tier "A" кандидатам з подібним мінусом, а 🧭 Стратег звіряється з
  ними, будуючи новий пошуковий запит. У промпт передаються тільки 20
  найновіших прикладів (`MAX_FEEDBACK_ENTRIES_IN_PROMPT`) - без ліміту
  список ріс би без кінця і роздував би вартість кожного виклику Claude.
  Чесно варто пам'ятати: це навчання на СМАКАХ конкретної рекрутерки, а не
  на об'єктивній істині - якщо колись позначиш причину помилково, скористайся
  кнопкою "🗑️ Очистити фідбек" у сайдбарі, інакше AI буде відтворювати цю
  помилку в кожному наступному пошуку.

## Це вже команда, а не один інструмент

П'ять ролей працюють по черзі над кожним кандидатом і перевіряють одна
одну, а не один суцільний "чорний ящик" - у логу вони підписані іменами,
щоб було видно, хто саме зараз щось вирішив:

- 🧭 **Стратег** - будує й перебудовує пошуковий запит, враховує твої корективи.
- 🛠️ **Механік** (PM-агент) - лагодить технічні збої Apify-запиту і
  запам'ятовує рішення назавжди (див. "Самонавчання" вище).
- 🗂️ **Ашбі** (ATS Checker) - звірка з Ashby, поки заглушка без ключа.
- ⚖️ **Суддя** (Strict Evaluator) - жорстка оцінка: локація, стоп-лист, грейд, тір.
- 🔍 **Скептик** (Critic) - перевіряє Суддю на галюцинації, пропускає далі
  тільки "чистих" кандидатів.

Важливо чесно розуміти: це імена для зручності читання логу, а не окремі
AI-моделі з власною свідомістю чи пам'яттю - усі п'ятеро це той самий
Claude, просто з різними інструкціями під різну задачу. Спільна пам'ять
про вирішені проблеми (вище) - ось що реально робить це "командою, яка
вчиться", а не просто красивими підписами.

Перед стартом пошуку 🧭 Стратег також коротко "бриф" з тобою: дивиться
опис вакансії і, якщо там бракує чогось критичного (напр. немає локації
чи не зрозуміло, який грейд), ставить 1-2 уточнюючі питання. Якщо опису
й так достатньо - питань не буде, пошук почнеться одразу.

Важливий нюанс: пам'ять про вирішені проблеми зараз спільна на весь
Apify-акаунт (весь, хто користується цим самим токеном, бачить ті самі
уроки) - для одного рекрутера чи невеликої команди це навіть плюс
(спільний досвід), але варто знати про це наперед.

Свідомо залишили чекпоінт-архітектуру як є (зупинка й проміжний звіт
після КОЖНОЇ ітерації, а не "запусти і забудь до фіналу") - це те, що
ти сама обрала, коли ми це обговорювали. Причина та сама, що й раніше:
Streamlit не вміє "заморозити" один суцільний цикл і чекати відповіді в
реальному часі, а тобі важливо мати змогу втрутитись, тож чекпоінт після
кожної ітерації лишається правильною архітектурою саме для цього
інструменту.

## Технічні покращення (стабільність, швидкість, вартість)

- **Гарантований JSON без regex (Tool Use).** Раніше кожна відповідь Claude
  парсилась регуляркою, яка шукала перший "{" і останній "}" у вільному
  тексті - нестабільно, якщо модель випадково згадає фігурні дужки де
  завгодно в поясненні. Тепер усі 5 викликів (`ask_claude_tool`) примушують
  Claude відповісти СТРОГО через Tool Use (`tool_choice`) - Anthropic API сам
  гарантує валідний JSON за схемою, без жодного regex чи `json.loads` над
  вільним текстом. Це, ймовірно, і була справжня причина одного з випадків,
  коли Стратег не міг згенерувати нормальний запит.
- **Повторні спроби з паузою.** Якщо виклик Claude все ж не спрацював
  (rate limit, короткий мережевий збій) - до 2 повторних спроб з паузою, що
  зростає (1с, 2с), перш ніж здатись. Раніше одна випадкова помилка одразу
  штовхала Strategist/PM у аварійний fallback-режим (сирий, непридатний
  запит - буквально перші 100 символів опису вакансії як текст пошуку).
  Тепер, якщо fallback все ж стався, у логу видно ТЕКСТ реальної помилки, а
  не мовчазну деградацію.
- **Паралельна перевірка кандидатів.** ATS -> Evaluator -> Critic для кожного
  кандидата тепер виконується пачками по 3 одночасно (`MAX_CANDIDATE_WORKERS`
  в коді) замість строго по одному - помітно швидше на пулі з 20+ кандидатів.
  Свідомо не 5+ одночасно: більше паралельних запитів до Claude API - це
  прямий ризик rate limit, а ми вже мали такий випадок.
- **Дешевший Google X-ray.** Перш ніж платити за повний скрапінг профілю
  (`fetch_linkedin_profiles_by_url`) для КОЖНОГО посилання, знайденого через
  Google, - безкоштовний фільтр за заголовком/сніпетом з видачі Google
  відсіює явно нерелевантні профілі (Google іноді повертає посилання на
  LinkedIn, які ніяк не про шукану роль). У логу видно, скільки відсіяно.
- **Пам'ять про перевірених кандидатів - окремо на кожну вакансію.** `seen_urls`
  тепер теж зберігається в персональному Apify Key-Value Store (як і уроки
  вище), але СВІДОМО в окремому сторі з ключем, прив'язаним до конкретного
  опису вакансії (хеш тексту), а не спільно на все. Це означає: кандидат,
  якого вже перевіряли для "Product Analyst", не скрапиться і не оцінюється
  повторно, якщо знову шукати на ТУ Ж вакансію - але залишиться видимим для
  геть іншої вакансії ("Marketing Manager" через рік). Це твій вибір - ми
  свідомо не зробили цю пам'ять спільною на всі вакансії, щоб хороші
  кандидати не зникали назавжди через непов'язаний пошук у минулому.

## Чому тут немає "команди з 11 AI-агентів"

Якщо порівнювати з великими multi-agent системами (окремі персонажі-агенти,
автономний нічний запуск через GitHub Actions, спільний репозиторій, на
якому агенти самі комітять фікси) - свідомо НЕ будували цього тут. Причина
проста: та архітектура вирішує проблему команди, яка постійно розробляє й
підтримує великий кодовий продукт з багатьма сервісами. Наш інструмент - це
один Streamlit-скрипт з одним завданням (сорсинг кандидатів), не команда
розробки. Автономний запуск "вночі без людини" також вимагав би окремого
сервера/раннера - це вже інша, значно важча інфраструктура, не MVP. Взяли з
цієї ідеї тільки те, що реально підходить під наш масштаб: пам'ять про
вирішені проблеми (вище) і сам PM-агент, який шукає корінь проблеми, а не
зупиняється на першому симптомі.

## Що ще НЕ підключено (свідомо, за домовленістю)

Ashby-інтеграція (Agent 2) - зараз заглушка. Без Ashby Admin API key кандидат
просто позначається "Не перевірено в ATS" і йде далі по циклу. Коли буде
ключ - шукай коментар `TODO ASHBY` в `app.py`, там точно описано, що саме
дописати (candidate.search + application.list + звірка hiring team).

Важливо: Ashby підключається напряму через REST API (Admin API key), а не
через MCP - MCP працює всередині Claude/Cowork-чату, а не всередині
окремого Streamlit-додатку, який відкривається в браузері як самостійна
сторінка.

## Запуск локально

```bash
pip install -r requirements.txt
streamlit run app.py
```

Відкриється сторінка в браузері. Введи Anthropic API key і Apify API token
в лівій панелі - без них кнопка "Почати пошук" не запуститься.

## Деплой на Streamlit Community Cloud (безкоштовно)

1. Заведи GitHub-репозиторій, залий туди `app.py` і `requirements.txt`.
2. Зайди на https://share.streamlit.io, натисни "New app".
3. Вибери репозиторій, гілку `main`, файл `app.py`.
4. Натисни Deploy.
5. Ключі API вводяться прямо у формі додатку в браузері - нічого додатково
   налаштовувати на Cloud не треба.

## Про вартість і швидкість (важливо розуміти наперед)

Кожен кандидат, що доходить до серйозної перевірки, - це 2 виклики Claude
(Evaluator + Critic). Плюс окремий виклик Claude на кожну ітерацію
(Strategist) і один платний запуск Apify-актора на ітерацію. Для пошуку
10 ідеальних кандидатів з нуля реально вийде 30-60+ платних API-викликів
за одну сесію. Це нормально для MVP, але варто закладати бюджет і час
(кожна ітерація - це реальний запуск скрапера, не миттєво).

Якщо увімкнений Google X-ray - додається ще 2 платні виклики Apify за
ітерацію (Google-пошук + дотягування повних профілів за URL). Це той самий
Apify-акаунт і токен, просто окремий рахунок за events на ньому. Обидва
актори (`apify/google-search-scraper`, `harvestapi/linkedin-profile-scraper`)
працюють по моделі pay-per-event - точні ціни дивись у вкладці Pricing
кожного актора в Apify Console.

## Відомі обмеження MVP

- CSV-експорт для Ashby - орієнтовний формат. Точні назви колонок для
  реального імпорту треба звірити з вашим Ashby-акаунтом.
- Точні назви полів у відповіді Apify-актора можуть відрізнятись між
  запусками - код читає декілька можливих варіантів назв, але раджу
  один раз глянути на сирий результат в Apify Console, якщо щось
  відображається як "н/д".
- Визначення "українець/росіянин" - це евристика AI за текстом профілю
  (локація, мова, освіта), а не перевірений факт. Завжди перевіряй
  вручну перед аутричем.
